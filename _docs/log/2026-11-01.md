## #77 Publish app images to GHCR

### What was done
- Added `.github/workflows/images.yml`: on a push to any branch it builds the backend and frontend images (linux/amd64, `load: true`, GitHub Actions layer cache, OCI labels revision and source), runs `make check-image-contents`, runs Trivy (config scan of the Dockerfiles, then each image; critical/high with a fix fails; SARIF files), uploads the SARIF files, and only then logs in to GHCR with `GITHUB_TOKEN` and pushes the scanned images as `ghcr.io/davbaster/mcp-lab-backend:<sha>` and `-frontend:<sha>` (`make push-images`). `packages: write` and `security-events: write` are on the one job only. Fork pull requests run the same job on a GitHub-hosted runner with the push, login and upload steps skipped.
- Added Makefile targets `check-image-contents`, `push-images`, `upload-sarif` (with HELP lines), `backend/scripts/check_image_contents.py` (no env file in either image, no quiz data in the frontend image, reusing helpers of `check_images.py`), `backend/scripts/upload_sarif.py` (uploads SARIF with the token, stdlib only, so `github/codeql-action/upload-sarif` is not needed), and an empty `.trivyignore`.
- README: new "Published images" section; CI paragraph mentions both workflows.
- Pinned actions: setup-buildx-action v4.4.1, login-action v4.7.0, build-push-action v7.4.0, trivy-action v0.36.0 (Trivy v0.70.0 is its default).
- Checked locally: actionlint (docker image) clean on images.yml; both images built; Trivy 0.70.0 on both images and on a clean copy of the repo; `make check-image-contents` passes on the built images and fails on an image with `.env` files and a `private` folder; `make check-images`; `test_repo_files.py` and `test_check_images.py` (62 passed); ruff.

### Decisions made (and why)
- The images are scanned and checked in the local Docker daemon and then `docker push`ed (not rebuilt), so the pushed image is the scanned one.
- `upload_sarif.py` instead of `upload-sarif`, because that action is not approved and `run:` lines must be `make` targets.
- Same-repo pull requests do not run the workflow: the push of their branch already did, and a pull request run would build a merge commit that is on no branch. Pushes are not cancelled by newer pushes (every commit needs images).
- Fork pull requests run on `ubuntu-24.04` (GitHub-hosted), since ci.yml's rule is that fork code never runs on the self-hosted runner and the issue wants forks to build.
- `VITE_APP_VERSION` is the commit SHA for the frontend image.
