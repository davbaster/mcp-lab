## #39 Ops schema and database roles

### What was done
- Branch `feat/39-ops-schema-roles`. New Python part `oncall-mcp/` (`pyproject.toml` with the same specs as the backend, `uv.lock`, `.python-version` 3.12, `alembic.ini`, `oncall_mcp/{db,models}.py`, `migrations/env.py`).
- `env.py` reads `OPS_DATABASE_URL`, keeps its version table at `ops.ops_alembic_version`, compares only the `ops` schema, and creates the schema before the version table is used.
- Migration 0001: the seven `ops` tables with their CHECK, UNIQUE and partial unique constraints, real downgrade. Migration 0002: the four LOGIN roles and grants; passwords from env vars, hashed (SCRAM-SHA-256) before they reach Postgres.
- Makefile targets `install-oncall-mcp`, `lint-oncall-mcp`, `migrate-oncall-mcp`, `check-migrations-oncall-mcp` (install and lint are in the aggregates), a CI job `oncall-mcp` with a Postgres service, `.env.example`, both READMEs and `AGENTS.md`. The exact-list assertions in `backend/tests/test_repo_files.py` were updated for the new targets (no new tests).
- Checked by hand against the disposable test Postgres: upgrade, downgrade to base, upgrade again, `alembic check` clean, a SQL script (kept outside the repo) with 64 checks of every constraint and every role's grants, and a real login with each role. `make lint`, `make check`, and the whole backend suite (see Errors).

### Decisions made (and why)
- `ops_writer` also gets SELECT on its tables: an `UPDATE ... WHERE` and an `INSERT ... RETURNING` need it. `audit_log` stays INSERT only (no read).
- Downgrade of 0001 drops the tables but leaves the empty `ops` schema: it holds the version table, which Alembic updates after the step, so `DROP SCHEMA` would fail. `env.py` re-creates it if missing.
- `ops.alerts` column is `course_id` (not `course`), as the repo rule says every course-related table carries `course_id`. Allowed values for alert status (`firing`, `resolved`) and severity (`critical`, `warning`, `info`) are proposals. Every table has a UUID `id` generated by the database (`gen_random_uuid()`), `ops.alerts` too.
- The CI job is the last one in `ci.yml`, so the tests that slice the `backend` job text by the next job name stay unchanged. There is no `ci-ok` job yet (#90), so nothing to add there.
- Roles are created without a password in any statement, log or error: the SCRAM verifier is computed in the migration.

### Open threads
- No pytest for the constraints and roles (the no-new-tests decision); the acceptance criterion "a test checks each constraint" is covered only by the manual SQL script.
- Makefile and CI for `oncall-mcp/` were added here instead of in #40.
- The grants on `app.*` happen only if `app.feedback` exists when 0002 runs (isolated mode keeps the app elsewhere); a re-runnable grant script is still to write. A column added to `app.feedback` later is not readable by `oncall_reader` until the grant is run again.
- The evidence columns of the retention job (#64, dropped) are not covered by `ops_retention`.
- `deployment` is stored as the deployment's name (text), not a foreign key.
- Creating roles needs CREATEROLE (or a superuser).
- The existing backend test `test_alembic_check_ignores_other_schemas` creates and drops an `ops` schema in the backend test database, so it fails while the real `ops` schema is there. Run the `ops` migrations on another database locally (documented in `oncall-mcp/README.md`).
